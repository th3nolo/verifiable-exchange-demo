# Recovery and publication contract

Area B integration interface (2026-10-03, root v5 / schema 13).

`store::ExecutionState` holds `root_version: u32`, `mid_windows: BTreeMap<String, MidWindowRow>` and `extensions: BTreeMap<String, Vec<u8>>`. `Change::ExecutionState` writes this full snapshot inside the transaction that writes book, trades, cursor and claim. `MatcherState::execution_state()` supplies it in `take_pending()`. Sorted maps make the JSON encoding deterministic. MidWindow includes ordered timestamp/optional-mid samples and clipping time; cached integer sums are reconstructed.

D should put **the complete `Ledger::canonical_bytes()`** under extension key `ledger-v1`, including mode, funding config, sequence, balances and reservations. Set it at genesis and after every state transition, before calculating roots or taking the pending batch. `set_execution_extension(String, Vec<u8>)` and `execution_extension(&str) -> Option<&[u8]>` expose that boundary. Restore through `Ledger::from_snapshot(serde_json::from_slice(bytes)?)` and `validate_open_orders`; never derive reservations from book or inject funding on resume. Missing/invalid ledger bytes in a funded run must reject recovery. B does not implement D's hooks in this separate worktree; integration must connect them before closing the root version.

Confirmed D APIs in its worktree: `ledger_snapshot() -> LedgerSnapshot`, `ledger_canonical_bytes() -> Vec<u8>`, `restore_ledger(LedgerSnapshot) -> Result<(), LedgerError>`. Integration should generate the ledger bytes from the current typed ledger directly inside `execution_state()` and before root hashing; do not use a cached extension left over from an earlier cancel/delist/rejection. After rebuilding books and cursor, pass the stored payload to `restore_ledger` before comparing roots. That hook validates cursor, conservation and every open-order reservation. C's `ResourceLimits` needs a similarly typed restore hook and unknown-version rejection.

Schema 13 adds epoch, root_version and execution_state without replacing historical claims. Existing nonempty v4 snapshots reject resume with a diagnostic: MidWindow was not recorded, so equivalent future Market execution cannot be established. Reset is explicit and preserves rows. `state_root_for_version(4)` retains the historical encoding; new state roots use v5. The integrator must route historical replay verification by the recorded version and include the ledger snapshot at every root boundary.

The trusted matcher key comes from the separate key file before snapshot reconstruction. Recovery verifies the last claim's signature, session, range, cursor, trade count and root binding before comparing its authenticated root with rebuilt state. This does not detect rollback of the entire DB to an older valid signed checkpoint; that needs an independently retained latest checkpoint. Compromising both key file and DB is outside this trust boundary.

Each Store ownership generation fences commit, heartbeat, close and metadata writes. Commit obtains SQLite's write transaction before checking epoch and cursor, so takeover cannot interleave the check and mutation. Old owners cannot close the new owner's run or rewind its cursor.

Durable polling executes on a private candidate state. Only successful SQLite commit swaps the candidate into the shared API state and emits a stream tick. Any persistence/fencing failure pauses execution and retains the last published committed state. Recovery requires operator restart after restoring storage. `--no-state-db` explicitly selects volatile mode: memory publication is immediate, no durable history/ACK is promised, and `durable_feed_id` remains zero. `/market` exposes persistence mode and paused state.

Limit: candidate cloning costs O(current state) per batch. This is a correctness-first implementation; throughput and memory overhead require measurement. Process/SQLite fault tests do not establish power-loss durability. Unix LD_PRELOAD disk tests, remote service behavior, and on-chain operations are not verified here.
