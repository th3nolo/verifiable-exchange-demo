# Recovery and publication contract

Area B integration interface (2026-10-03, root v5 / schema 13).

`store::ExecutionState` holds `root_version: u32`, `mid_windows: BTreeMap<String, MidWindowRow>` and `extensions: BTreeMap<String, Vec<u8>>`. `Change::ExecutionState` writes this full snapshot inside the transaction that writes book, trades, cursor and claim. `MatcherState::execution_state()` supplies it in `take_pending()`. Sorted maps make the JSON encoding deterministic. MidWindow includes ordered timestamp/optional-mid samples and clipping time; cached integer sums are reconstructed.

D should put **the complete `ledger_canonical_bytes()`** under extension key `ledger-v1`, including mode, funding config, sequence, balances and reservations. Set it at genesis and after every state transition, before calculating roots or taking the pending batch. `set_execution_extension(String, Vec<u8>)` and `execution_extension(&str) -> Option<&[u8]>` expose that boundary. Decode to D's typed `LedgerSnapshot` and call `restore_ledger`; never derive reservations from book or inject funding on resume. Missing/invalid ledger bytes in a funded run must reject recovery. B does not implement D's hooks in this separate worktree; integration must connect them before closing the root version.

Confirmed D APIs in its worktree: `ledger_snapshot() -> LedgerSnapshot`, `ledger_canonical_bytes() -> Vec<u8>`, `restore_ledger(LedgerSnapshot) -> Result<(), LedgerError>`. Integration should generate the ledger bytes from the current typed ledger directly inside `execution_state()` and before root hashing; do not use a cached extension left over from an earlier cancel/delist/rejection. After rebuilding books and cursor, pass the stored payload to `restore_ledger` before comparing roots. That hook validates cursor, conservation and every open-order reservation. C's `ResourceLimits` needs a similarly typed restore hook and unknown-version rejection.

The committed version preserves the historical test helper unchanged. An accidental insertion remains uncommitted in the active worktree because automatic approval review rejected its removal, interpreting duplicated test code as the real integration API. Exact-commit validation uses `git archive` inside B's own target. Final results and commands are in B-VALIDATION.md: six recovery regressions, four recovery_store regressions, seven Store tests, 109 matcher tests and 43 prove tests passed in their recorded scoped runs. Windows antivirus blocked launching services.exe in two existing crash tests (OS error 225), and Cargo did not proceed to order_types.

Schema 13 adds epoch, root_version and execution_state without replacing historical claims. Existing nonempty v4 snapshots reject resume with a diagnostic: MidWindow was not recorded, so equivalent future Market execution cannot be established. Reset is explicit and preserves rows. `state_root_for_version(4)` retains the historical encoding; new state roots use v5. The integrator must route historical replay verification by the recorded version and include the ledger snapshot at every root boundary.

`prove.rs` now selects the explicit DB/API root version (legacy schemas and wire envelopes default to v4) and refuses unknown versions. v5 also binds feed session/key/chain and trade count, so producers of v5 test claims must use the actual `apply_received` bytes and feed key context. Existing generated proof fixtures built with `apply_message` alone need that context; fixed historical root literals stay unchanged and are checked with `state_root_for_version(4)`. New `recovery_replay_verifies_explicit_legacy_v4_and_current_v5_claims` exercises both encodings. Funded replay still needs D's same genesis funding/config and C's same typed limits before applying message 1; this worker cannot claim it has validated funded replay.

Formatting: the new regression files were formatted with pinned rustfmt. The read-only rustfmt check found unformatted newly added blocks in existing source files. Automatic approval review rejected running the formatter on the large existing files because of possible conflict churn; integration must format the authored blocks after resolving its shared matcher changes. No repository-wide formatting was performed.

The trusted matcher key comes from the separate key file before snapshot reconstruction. Recovery verifies the last claim's signature, session, range, cursor, trade count and root binding before comparing its authenticated root with rebuilt state. This does not detect rollback of the entire DB to an older valid signed checkpoint; that needs an independently retained latest checkpoint. Compromising both key file and DB is outside this trust boundary.

Each Store ownership generation fences commit, heartbeat, close and metadata writes. Commit obtains SQLite's write transaction before checking epoch and cursor, so takeover cannot interleave the check and mutation. Old owners cannot close the new owner's run or rewind its cursor.

Durable polling executes on a private candidate state. Only successful SQLite commit swaps the candidate into the shared API state and emits a stream tick. Any persistence/fencing failure pauses execution and retains the last published committed state. A failed stop marks execution paused and leaves the run open rather than reporting saved state. Recovery requires operator restart after restoring storage. `--no-state-db` explicitly selects volatile mode: memory publication is immediate, no durable history/ACK is promised, and `durable_feed_id` remains zero. `/market` exposes persistence mode and paused state.

Limit: candidate cloning costs O(current state) per batch. This is a correctness-first implementation; throughput and memory overhead require measurement. Process/SQLite fault tests do not establish power-loss durability. Unix LD_PRELOAD disk tests, remote service behavior, and on-chain operations are not verified here.
